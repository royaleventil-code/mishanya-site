# Анкета QR-подарка `/gift`

- Production: `https://mishanya-show.com/gift?src=banner-01`.
- Страница закрыта от индексации и не содержит WhatsApp-призыва.

## Локальная работа

- Страница: `http://localhost:3003/gift?src=banner-01`.
- В `npm run dev` отправка работает через локальный mock и ничего не записывает в Bitrix или Cloudflare.
- Первый подарок сохраняется в `localStorage` по нормализованному международному номеру.
- Повторная отправка с тем же номером показывает уже закреплённый подарок и не меняет его.
- Поле телефона — обычный свободный ввод без выбора страны. Израильский номер можно указать в местном формате, а номер другой страны нужно ввести полностью с кодом страны. После проверки в Bitrix номер сохраняется в E.164.
- Поле ведущего обязательно и ограничено утверждённым списком: Мишаня, Артур Фокусник, Артур Сумасшедший Профессор, Ханна, Ира, Женя, Леон или `Не знаю, кто ведущий`.
- При выборе `Двое детей` сразу открываются две карточки. Кнопкой `Добавить ещё ребёнка` можно добавить третьего и следующих детей (до восьми); добавленные карточки можно убрать. Пол, возраст и ближайший день рождения указываются отдельно для каждого ребёнка, поддерживаются любые сочетания пола.

## Что записывается в Bitrix после подключения

Основной ребёнок — ребёнок с ближайшей будущей датой дня рождения:

- `NAME` — имя клиента;
- `PHONE` — телефон в международном формате E.164 (`+972...`, `+380...`, `+1...` и другие) с типом `WORK`, который используют WhatsApp-роботы Bitrix24;
- `UF_CRM_1644328015350` — город;
- `UF_CRM_1644327962757` — пол основного ребёнка (`44` мальчик / `46` девочка);
- `UF_CRM_1644329391894` — сколько лет исполнится;
- `BIRTHDATE` — ближайшая будущая дата дня рождения;
- `UF_CRM_1649234588017` — та же дата для рассылки;
- `UF_CRM_1644332749977` (`Ждать до`) — за 32 дня до ближайшего дня рождения; если дата выпадает на субботу, переносится на следующее воскресенье (31 день до дня рождения);
- `UF_CRM_1666781395585` — `808` (`День рождения`);
- `UF_CRM_1784446465040` (`Выбранный подарок`) — выбранный клиентом подарок на русском языке;
- `ASSIGNED_BY_ID` — `3828` (Сергей);
- новый лид создаётся на первой стадии `Новый лид` (`STATUS_ID = NEW`);
- `SOURCE_ID` — `QR_PARTY_GIFT` (`QR-код с праздника`);
- `COMMENTS` — видимое в карточке поле `Заметка`.

В `Заметке` сохраняются только дата анкеты, подарок, выбранный ведущий и найденные совпадения по телефону. Дата окончания действия подарка в `Заметку` не записывается. Имя, телефон, город, язык интерфейса, носитель QR и данные основного ребёнка там не дублируются. Если указан один ребёнок, сведения о детях в `Заметку` не добавляются. Если детей несколько, в основные поля попадает ребёнок с ближайшим ДР, а в `Заметку` по порядку добавляются только пол, возраст и ближайшая дата остальных детей. В D1 выбранный ведущий и все дети остаются в структурированном зашифрованном payload.

Служебные подписи, подарок, пол ребёнка и описание источника всегда записываются в Bitrix на русском, даже если интерфейс анкеты был на иврите. Имя клиента и город сохраняются ровно так, как их ввёл клиент, чтобы не искажать собственные имена.

Интеграция не меняет стадию после создания, не переносит лид в реактивацию и не обновляет старые карточки. Поле `Ждать до` сразу получает дату за 32 дня до ближайшего дня рождения. Если эта дата выпадает на субботу, она переносится на следующее воскресенье, то есть на 31 день до дня рождения. Дальнейшее решение по каждому новому лиду Сергей принимает вручную.

## Защита от дублей

1. D1 проверяет активный подарок по HMAC-хешу нормализованного телефона.
2. Пока подарок действует, новый выбор не перезаписывает его.
3. Bitrix проверяется через `crm.duplicate.findbycomm`.
4. Для каждой новой действительной анкеты создаётся новый лид на первой стадии.
5. Существующие лиды, контакты и компании автоматически не обновляются и не связываются.
6. ID найденных карточек записываются в `Заметку`, чтобы Сергей принял решение вручную.
7. Повторная отправка той же анкеты защищена внешним ID и не создаёт второй лид.

## Надёжная доставка

1. Pages Function валидирует анкету и первой операцией сохраняет её в D1.
2. Turnstile проверяется, когда защитный виджет доступен. Если браузер блокирует его, форма продолжает работать: спам ограничивают скрытое поле-ловушка и лимит 12 попыток с одного IP в час в D1.
3. В очередь `mishanya-gift-sync` отправляется только ID анкеты без персональных данных.
4. Worker расшифровывает запись, проверяет дубли и создаёт лид в Bitrix.
5. При временной ошибке сообщение повторяется до 10 раз и затем попадает в `mishanya-gift-sync-dlq`.
6. `ORIGINATOR_ID` + `ORIGIN_ID` защищают от повторного создания лида при повторной доставке сообщения.

## Cloudflare bindings и secrets

Pages project `mishanya-site`:

- D1 binding `GIFT_DB` -> `mishanya-gift`;
- Queue producer binding `GIFT_SYNC_QUEUE` -> `mishanya-gift-sync`;
- encrypted secrets `GIFT_DATA_SECRET` и `TURNSTILE_SECRET_KEY`;
- GitHub variable `NEXT_PUBLIC_TURNSTILE_SITE_KEY`.

Worker `mishanya-gift-sync`:

- D1 binding `GIFT_DB` -> `mishanya-gift`;
- Queue consumer `mishanya-gift-sync`;
- encrypted secrets `GIFT_DATA_SECRET` и `BITRIX_WEBHOOK_URL`;
- variable `BITRIX_QR_SOURCE_ID = QR_PARTY_GIFT`.

Production workflow обязан публиковать и Cloudflare Pages, и Worker `mishanya-gift-sync`. Изменения `shared/gift-core.js` не попадают в обработчик очереди, пока Worker не выполнит отдельный `wrangler deploy`.

Для выбранного подарка используется пользовательское поле лида `UF_CRM_1784446465040`. Все секреты хранятся в Cloudflare и не попадают в GitHub или клиентский JavaScript.

## D1

Схема находится в `migrations/0001_gift_claims.sql`, `migrations/0002_gift_sync.sql` и `migrations/0003_gift_rate_limits.sql`. Database ID не является секретом; реальные секреты в репозиторий не добавляются.
