# Workflow сайт Мишаня

## Контекст работы

Над сайтом работают минимум два человека на разных компьютерах. Поэтому локальная версия сайта у Сергея, версия второго участника и версия на GitHub могут отличаться.

Рабочая папка сайта:

`D:\Cloude CODE\1. Продажи Мишаня\New SITE`

GitHub-репозиторий:

`https://github.com/royaleventil-code/mishanya-site.git`

## Правило перед началом работы

Если Сергей пишет только «продолжаем работать по сайту» или похожую фразу без конкретной задачи, стартовое действие одно:

1. Открыть локальный сайт `http://localhost:3003/`.
   Порт `3003` закреплен за этим проектом, чтобы не мешать параллельной работе CRM на `3000`.
2. Ничего не придумывать и не искать, где остановились.
3. Ждать конкретную задачу от Сергея.

В начале новой рабочей сессии по сайту нужно один раз свериться с GitHub, если Сергей не сказал иначе:

1. Проверить текущую ветку и локальные изменения.
2. Проверить, есть ли на GitHub версия новее локальной.
3. Если на GitHub есть новые изменения, сначала подтянуть их.
4. Только после этого начинать править сайт.

После успешной стартовой сверки, если GitHub не был новее локальной версии, в течение этой же рабочей сессии не проверять GitHub перед каждой правкой. Работать локально, вносить только правки по команде Сергея. Push делать только когда Сергей прямо скажет запушить.

## Если локальная версия новее GitHub

Если после проверки видно, что локальная версия опережает GitHub, ассистент не пушит сам молча.

Сначала нужно спросить Сергея:

`Локальная версия сайта новее GitHub. Залить её на GitHub?`

Только после подтверждения Сергея можно делать commit/push.

## Если есть локальные незакоммиченные изменения

Если в рабочей папке есть незакоммиченные изменения:

1. Не затирать их.
2. Не делать reset/checkout без прямой просьбы Сергея.
3. Сначала коротко сообщить, какие файлы изменены.
4. Если pull может конфликтовать с локальными изменениями, остановиться и спросить Сергея, что делаем: сохранить, закоммитить, отложить или разобрать вручную.

## Локальная работа в течение дня

Сергей сам управляет последовательностью задач по сайту. Ассистент не выбирает следующий кусок работы самостоятельно, не отмечает страницы/программы как готовые без прямой команды и не делает выводы вида «очевидно, следующий шаг такой-то».

Сайт сначала правим локально.

Порядок:

1. Запустить локальный сервер сайта на порту `3003`, если он не запущен.
2. Открыть локальный сайт `http://localhost:3003/`.
3. Вносить только те правки, которые Сергей прямо попросил.
4. После стартовой сверки не проверять GitHub повторно перед каждой локальной правкой.
5. После каждой значительной правки обязательно выполнить полный локальный тест по разделу «Обязательная проверка после значительной правки».
6. Не выдавать Сергею финальный ответ о готовности, пока обязательная проверка не завершилась без ошибок.
7. В течение рабочего процесса не пушить каждую мелкую правку на GitHub.
8. В конце рабочего дня собрать готовые изменения, коротко показать Сергею итог и спросить подтверждение на push.

GitHub используем как общую точку синхронизации, а не как место для каждой промежуточной правки.

## Что означает команда «push»

В этом проекте слова Сергея `push`, `пуш`, `запушить`, `пушим` и аналогичные формулировки означают **полностью выпустить согласованные изменения на продакшн**, а не просто отправить отдельную ветку на GitHub.

После такой команды ассистент обязан:

1. Убедиться, что обязательная локальная проверка изменений пройдена полностью; если нет — сначала завершить её.
2. Включить в выпуск только согласованные изменения сайта и не захватывать посторонние локальные файлы.
3. Доставить изменения в production-ветку `main`: напрямую или через обычный PR с последующим merge.
4. Не останавливаться на feature-ветке, открытом PR или draft PR.
5. Дождаться завершения production-деплоя и проверить живой сайт `https://mishanya-show.com/`, включая изменённый пользовательский сценарий.
6. Только после успешной проверки продакшна сообщить Сергею, что push завершён.

Отдельную ветку, обычный PR или draft PR без выпуска на продакшн создавать только тогда, когда Сергей прямо попросил именно ветку, PR или черновик. Если выпуск заблокирован конфликтом, ошибкой CI/деплоя или отсутствием доступа, не называть push завершённым — коротко сообщить конкретный блокер.

## Обязательная проверка после значительной правки

Значительной считается правка, которая затрагивает интерфейс, форму, пользовательский сценарий, бизнес-логику, интеграцию, маршруты, локализацию, аналитику, SEO, зависимости, конфигурацию сборки или поведение сайта в production.

После каждой такой правки ассистент обязан:

1. Запустить все относящиеся к изменению автоматические тесты.
2. Запустить `npm run lint`.
3. Запустить `npm run build` и убедиться, что production-сборка завершилась успешно.
4. Запустить или переиспользовать локальный сервер только на `http://localhost:3003/`.
5. В реальном браузере полностью пройти изменённый пользовательский сценарий, а не ограничиваться открытием страницы.
6. Если правка касается двуязычной страницы, проверить русский и иврит.
7. Если правка касается интерфейса, проверить мобильную ширину и обычный компьютерный экран.
8. Проверить консоль браузера, неуспешные сетевые запросы, ошибки HTTP, сломанную верстку и состояния формы.
9. После найденной ошибки внести исправление и повторить затронутые проверки до чистого результата.
10. Только после успешного полного прогона сообщить Сергею, что работа готова.

Если какую-то обязательную проверку невозможно выполнить из-за внешнего сервиса, доступа или другого блокера, нельзя называть работу готовой. Нужно коротко указать, что именно проверено, что не проверено и какой конкретный блокер остался.

Для локальной проверки форм и интеграций использовать безопасный mock, если реальная отправка создаёт лид, сообщение, заказ или другое внешнее действие. Реальную отправку выполнять только когда она прямо входит в задачу или отдельно разрешена Сергеем.

## Базовый порядок работы

1. Открыть папку сайта.
2. Один раз проверить GitHub и локальное состояние в начале рабочей сессии.
3. Подтянуть GitHub, если там версия новее.
4. Если локальная версия новее GitHub, спросить Сергея про загрузку на GitHub.
5. После синхронизации выполнять задачи по сайту локально, без повторной сверки GitHub перед каждой правкой.
6. После значительных изменений выполнить полный обязательный локальный тест: тесты, lint, build, локальный сервер, браузерный сценарий и проверку ошибок.
7. Перед отправкой на GitHub показать Сергею кратко, что изменилось, и спросить подтверждение на push.

## Короткое правило

Сайт не правим вслепую и не ведём самостоятельно. В начале рабочей сессии один раз свериться с GitHub. Если новых данных на GitHub нет — дальше работать локально без повторных GitHub-проверок перед каждой правкой. На старте открыть `http://localhost:3003/` и ждать задачу. Правки только по команде Сергея. После каждой значительной правки обязательно полностью проверить её локально и только затем давать финальный ответ. Push — только по прямой команде Сергея.
